## 1. 목표

호스트가 앱 안에서 **초대 링크를 만들어 카카오톡으로 보내면**, 받은 사람이 링크를 열고
비밀번호만 정하면 바로 들어오게 만든다. 청소 담당은 **이메일 없이 아이디로** 로그인한다.

메일 서버를 붙이지 않는다. 네이버·한메일로 가는 초대 메일은 스팸함에 들어가기 일쑤라
링크를 카톡으로 보내는 편이 실제로 더 잘 도착한다.

## 2. 아이디 로그인 — 내부 이메일로 변환

Supabase Auth 는 비밀번호 로그인에 **이메일 또는 전화번호**만 받는다. 아이디는 못 쓴다.
그래서 아이디를 내부 이메일로 바꿔서 넘긴다.

```
아이디 cleaner1  →  cleaner1@ponam.local
```

- 이 주소로는 메일을 보내지 않는다. 인증 시스템 내부 식별자일 뿐이다
- **변환은 결정적(deterministic)이라 조회가 필요 없다.** 아이디로 이메일을 찾으려면
  남의 `profiles` 를 읽어야 하는데 RLS 가 막고 있다. 규칙으로 만들면 그 문제가 사라진다
- 상수는 한 곳에만 둔다: `src/lib/auth/identity.ts` 의 `INTERNAL_EMAIL_DOMAIN = 'ponam.local'`

```ts
export function toAuthEmail(input: string): string {
  const v = input.trim().toLowerCase();
  return v.includes('@') ? v : `${v}@${INTERNAL_EMAIL_DOMAIN}`;
}

export function toDisplayId(email: string): string {
  return email.endsWith(`@${INTERNAL_EMAIL_DOMAIN}`) ? email.split('@')[0] : email;
}
```

**아이디 규칙**: 소문자 영문·숫자·언더스코어, 3~20자. `^[a-z0-9_]{3,20}$`.
한글 아이디는 받지 않는다 — 폰에서 입력할 때 한영 전환 때문에 오히려 불편하다.

### 2.1 로그인 화면

입력칸을 **"아이디 또는 이메일"** 한 칸으로. 두 칸으로 나누지 않는다.

- `autoCapitalize="none" autoCorrect="off" inputMode="text"` — 폰에서 첫 글자 대문자 방지
- 안내 문구: "호스트에게 받은 아이디로 로그인하세요"
- 에러는 "아이디 또는 비밀번호가 맞지 않습니다"

### 2.2 표시

`/more` 의 내 정보, 멤버 목록, 담당자 이름 옆 등에서 이메일을 그대로 노출하지 말고
`toDisplayId()` 를 거친다. 청소 담당에게 `cleaner1@ponam.local` 은 혼란만 준다.

## 3. 마이그레이션 `supabase/migrations/20260817140000_invites_name.sql`

성격: **추가형** (컬럼 1개. DROP·UPDATE 없음)

```sql
alter table public.invites add column name text not null default '';
```

`invites` 의 나머지 컬럼(`email`, `role`, `token_hash`, `expires_at`, `accepted_at`, `created_by`)은
이미 이 용도로 설계돼 있다.

## 4. 초대 만들기 — owner 전용

`/more/members` 화면 안에서 처리한다. 별도 페이지를 만들지 않는다.

입력: **이름 · 아이디(또는 이메일) · 역할**

- 아이디는 2번의 정규식으로 검증. 이미 쓰는 아이디인지 `profiles.email = toAuthEmail(입력)` 으로 확인
- 역할은 `reservation` / `settlement` / `cleaning` 중 선택.
  **`owner` 는 초대로 만들지 않는다.** 필요하면 기존 멤버의 역할을 바꾼다

서버 라우트 `POST /api/invite/create` (service_role):

```
1. 호출자가 owner 인지 확인 (쿠키 세션으로 — service_role 로 우회하지 말 것)
2. token = base64url(crypto.randomBytes(32))
3. invites insert (email=내부이메일, name, role, token_hash=sha256(token),
                   expires_at=now()+72h, created_by=나)
4. 응답에 원문 token 을 딱 한 번 돌려준다
```

화면은 완성된 링크와 **복사 버튼**을 크게 둔다. 안내 문구가 링크와 함께 복사된다.

```
포남동 예약관리 초대입니다.
아래 링크를 열어 비밀번호를 정하면 바로 사용할 수 있어요.
아이디: cleaner1
https://ponam-booking.vercel.app/invite/xxxxx
(3일 안에 열어주세요)
```

"카카오톡으로 보내기" 같은 건 만들지 않는다. 복사해서 붙여넣는 게 더 확실하다.

**토큰 원문은 해시만 저장하므로 다시 볼 수 없다.** 링크를 잃어버리면 목록에서
**재발급**(기존 초대 취소 + 새로 생성)을 누른다.

## 5. 초대 수락

### 5.1 페이지 `src/app/invite/[token]/page.tsx`

로그인 없이 접근 가능해야 한다. **미들웨어 matcher 에서 `/invite` 를 제외할 것.**
(빠뜨리면 초대받은 사람이 `/login` 으로 튕긴다)

- 서버에서 토큰 유효성만 확인해 **이름·아이디·역할을 보여준다**
- 비밀번호 입력 2회(확인). 최소 10자
- 유효하지 않으면 "만료되었거나 이미 사용된 초대입니다. 호스트에게 다시 요청하세요."
  **어떤 이유인지 구분해서 알려주지 않는다** — 토큰 존재 여부가 새면 안 된다

### 5.2 라우트 `POST /api/invite/accept`

service_role 로 실행한다. 서버 전용이다.

```
1. sha256(token) 으로 invites 조회 — accepted_at is null, expires_at > now()
   없으면 400 (이유 구분 없이 같은 메시지)
2. auth.admin.createUser({ email: invite.email, password, email_confirm: true,
                           user_metadata: { name: invite.name } })
   → 트리거 handle_new_user 가 profiles 를 만든다 (is_active=false)
3. profiles update: role = invite.role, is_active = true, name = invite.name
4. invites update: accepted_at = now()
5. 200 응답
```

2·3·4 중간에 실패하면 사람이 손댈 수 없는 상태가 된다. **실패 지점을 로그에 남기고,
이미 계정이 만들어졌으면 그 사실을 응답에 담아** 호스트가 수동 활성화할 수 있게 한다.

성공하면 클라이언트가 방금 정한 비밀번호로 바로 로그인시키고 `/cleaning` 으로 보낸다.

## 6. 멤버 관리 `/more/members` — owner 전용

`owner` 가 아니면 이 메뉴를 `/more` 에 노출하지 않는다.

### 6.1 멤버 목록

이름 · 아이디(`toDisplayId`) · 역할 배지 · 상태(활성/해지됨).

- **역할 변경** — 즉시 반영
- **해지** — `is_active = false`. 확인 한 번.
  "해지하면 즉시 모든 화면이 막힙니다. 기록은 남습니다."
- **복구** — 다시 활성화
- **비밀번호 재설정** — 6.2

`owner` 자신의 역할 변경·해지는 버튼을 비활성화한다. DB 트리거가 마지막 owner 를 막고 있지만,
화면에서 눌러보고 에러를 보게 만들 이유가 없다.

### 6.1.1 이름 편집

`profiles.name` 기본값이 빈 문자열이라 멤버 목록·청소 담당자·건수 집계에서 이름이 안 나온다.

- **`/more` 내 정보에서 본인 이름을 고칠 수 있게 한다.** `profiles_update_self` 정책이
  이미 허용한다(역할·활성상태·이메일만 못 바꾼다). 마이그레이션 불필요
- **owner 는 멤버 목록에서 남의 이름도 고칠 수 있다.** `profiles_owner_all` 로 가능
- 초대로 들어온 사람은 `invites.name` 이 들어가므로 처음부터 이름이 있다
- 이름은 1~20자, 공백만 있는 값은 거부

이메일 폴백 자체는 남겨둔다 — 어떤 이유로든 이름이 비면 `(이름 없음)` 보다 식별 가능한 값이 낫다.

### 6.2 비밀번호 재설정 — 반드시 필요하다

아이디 계정은 이메일이 없어서 **"비밀번호 찾기"를 스스로 못 한다.**
호스트가 재설정해주지 못하면 비밀번호를 잊은 사람은 영영 못 들어온다.

`POST /api/members/reset-password` (owner 확인 후 service_role) →
`auth.admin.updateUserById(userId, { password })`

- 앱이 읽기 쉬운 임시 비밀번호를 만들어준다 (`ponam-4271` 형태 — 전화로 불러줄 수 있어야 한다)
- 화면에 한 번 보여주고 복사 버튼
- 첫 로그인 후 변경을 강제하지 않는다. 5명 쓰는 내부 앱에 마찰을 더할 이유가 없다

### 6.3 초대 목록

대기 중인 초대: 이름 · 아이디 · 역할 · 만료까지 남은 시간. **취소** / **재발급**.
만료된 초대는 흐리게 표시하고 재발급만 가능.

## 7. 보안 규칙

- 토큰은 **32바이트 랜덤**, `crypto.randomBytes(32)` 를 base64url 로. `Math.random()` 금지
- DB 에는 **SHA-256 해시만** 저장한다. 원문은 생성 응답에 한 번만 실린다
- 만료 **72시간**, **1회용**(`accepted_at`)
- 초대 링크는 그 자체가 자격증명이다. 로그에 찍지 않는다
- `/api/invite/create`, `/api/members/*` 는 **쿠키 세션으로 owner 여부를 먼저 확인**하고
  그다음에 service_role 을 쓴다
- `/api/invite/accept` 는 로그인 없이 호출되는 유일한 특권 라우트다. 토큰 검증 외에는
  아무것도 신뢰하지 않는다. 요청 본문의 role·email 은 **무시하고 invites 행에서만 읽는다**
- 실패 응답은 이유를 구분하지 않는다

흐름 검증 — 실제로 끝까지 해본다:

9. **해지** → 승인 대기 화면으로 가는가

11. cleaning 계정으로 `POST /api/invite/create` → 403 인가

## 실제 구현 노트

### 1. `@ponam.local` 은 Supabase 가 받는다 — 도메인 변경 불필요

착수 전에 실제로 시험했다. `ponam.local` 과 `ponam-booking.internal` **둘 다** 통과했다.

| 확인 | ponam.local | ponam-booking.internal |
|---|---|---|
| `auth.admin.createUser` | ✅ | ✅ |
| 그 계정으로 로그인 | ✅ | ✅ |
| `handle_new_user` → `profiles` 생성 | ✅ | ✅ |

덤으로 확인된 것 — **트리거가 `user_metadata.name` 을 `profiles.name` 에 넣는다.**
초대 수락 시 이름이 처음부터 채워지므로 5.2 의 3단계가 실패해도 이름은 남는다.

### 2. API 경로는 미들웨어에서 리다이렉트하면 안 된다

처음 구현에서 비로그인 `POST /api/invite/create` 가 **401 이 아니라 405** 를 돌려줬다.
미들웨어가 `/login` 으로 307 리다이렉트하고, 그 리다이렉트를 따라간 POST 가
GET 전용 페이지에 도달해 `405 Method Not Allowed` 가 된 것이다.

차단 자체는 되고 있었지만(핸들러에 도달하지 않음) API 로서는 잘못된 응답이다.
**미들웨어에서 `/api/` 경로는 리다이렉트하지 않고, 각 라우트의 `requireOwner()` 가
401/403 을 내도록** 고쳤다. 세션 쿠키 갱신은 그대로 한다.

### 3. 역할·활성상태 변경에 별도 라우트를 만들지 않았다

`profiles_owner_all` 정책이 owner 의 UPDATE 를 이미 허용한다. 클라이언트에서 직접
`update()` 하면 **RLS 가 곧 인가**가 된다. 라우트를 하나 더 만들면 그 안에서 권한을
다시 구현해야 하고, 그게 정책과 어긋날 여지가 생긴다.

service_role 이 꼭 필요한 것만 라우트로 뺐다 — 초대 생성(토큰), 초대 수락(비로그인),
비밀번호 재설정(`auth.admin`). 이 셋은 RLS 로 표현할 수 없는 일이다.

### 4. 재발급은 삭제 후 재생성이다

원문 토큰을 저장하지 않으므로 "다시 보여주기" 가 불가능하다. 기존 행을 지우고 새로 만든다.
그래서 재발급하면 **이전 링크는 즉시 죽는다** — 의도한 동작이다.
