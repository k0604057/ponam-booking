## 1. 목표

청소 담당이 "언제 청소할지 직접 정하고", 여유가 며칠인지 한눈에 보게 만든다.
그리고 예약 달력을 만든다.

## 2. 마이그레이션 — `planned_date` 추가

### 왜 새 컬럼인가

`cleaning_tasks.scheduled_date` 는 **퇴실일**이고 크롤러와 `sync_cleaning_task()` 트리거가 관리한다.
담당자가 고른 청소 예정일을 여기에 덮어쓰면 다음 동기화에서 퇴실일로 되돌아간다.
그래서 **원천 값(퇴실일)과 사람이 정한 값(청소 예정일)을 분리**한다.

### 파일 `supabase/migrations/20260817120000_cleaning_planned_date.sql`

성격: **추가형** (컬럼 1개, 인덱스 1개, 함수 1개. DROP·UPDATE 없음)

**적용 절차** — 요약 보고 → 사용자 "실행해" → `supabase db push` → 결과 보고 → `gen types` 재생성.

`claim_cleaning_task` 는 건드리지 않는다. 인자를 추가하면 replace 가 아니라 오버로드가 생겨
기존 함수를 drop 해야 하는데, 파괴형을 피하려는 것이다. 화면에서 **맡기 → 날짜 지정** 두 번 호출한다.

## 3. 청소 여유 기간 계산

카드에 날짜만 나와서는 부족하다. 실제로 필요한 정보는 **언제까지 끝내야 하는가**다.
숙소마다 예약이 일주일 단위이고 보통 2~3일을 비워두고 다음 예약을 잡는다.

```
퇴실일   = 이 청소 건의 scheduled_date
다음입실 = 같은 property_id 에서 status <> 'cancelled' 이고
           checkin_date >= 퇴실일 인 예약 중 가장 이른 checkin_date
마감일   = 다음입실이 있으면 → 다음입실일 (그날 입실 전까지 끝내야 함)
           없으면            → 퇴실일 + 3일
여유일수 = 마감일 - 퇴실일
```

표시:

| 상황 | 카드 첫 줄 |
|---|---|
| 다음 예약 있음 | `8/21(금) 퇴실 → 8/25(화) 입실 · 여유 4일` |
| 다음 예약 없음 | `8/21(금) 퇴실 → 다음 예약 없음 · 8/24(월)까지` |
| 당일 입실 | `8/21(금) 퇴실 → 당일 입실 · 오늘 안에` — 빨강 강조 |
| 여유 1일 | 주황 강조 |

`planned_date` 가 마감일을 넘으면 **"마감일 초과" 경고**를 카드에 표시한다. 저장은 막지 않는다 —
사정이 있을 수 있고, 막으면 사람이 앱을 우회한다.

## 4. 청소 보드 수정

### 4.1 카드 순서 — "내가 맡음"을 위로

```
1) 날짜·여유 기간 (3번 규칙)
2) 숙소 이름 + 상태 배지 + 경고 배지(일정 변경됨 / 마감일 초과)
3) 담당자 · [내가 맡음] / [놓기] 버튼
4) 청소 예정일 · [날짜 선택] 버튼      ← 맡은 뒤에만 노출
5) 메모
6) 사진
7) (시트 하단 고정) [청소완료]
```

### 4.2 맡기 → 날짜 선택

"내가 맡음"을 누르면 곧바로 **날짜 선택 시트**가 뜬다. 두 번 누르게 하지 않는다.

- 선택지는 **퇴실일부터 마감일까지의 날짜 버튼**을 나열한다. 캘린더 위젯보다 이게 빠르다.
  대개 3~4개다. 각 버튼에 `8/22(토)` 형식과 "퇴실 다음날" 같은 보조 문구
- 마감일 이후도 고를 수 있게 "다른 날짜" 항목을 하나 두고, 그때만 날짜 입력을 연다
- "나중에 정하기"로 건너뛸 수 있다. `planned_date` 는 null 로 남는다

```ts
await supabase.rpc('claim_cleaning_task', { p_task_id: id });
await supabase.rpc('set_cleaning_planned_date', { p_task_id: id, p_date: '2026-08-23' });
```

맡은 뒤에도 4)의 [날짜 선택]으로 언제든 바꿀 수 있다. 해제는 `p_date: null`.

### 4.3 그룹핑 기준 변경

섹션 분류와 정렬을 `coalesce(planned_date, scheduled_date)` 기준으로 한다.
담당자가 8/23에 가기로 했으면 8/23 섹션에 있어야 한다.

`밀린 청소` 판정도 같은 값 기준. 단 **마감일이 지났는데 미완료**면 예정일과 무관하게
밀린 청소에 넣는다.

### 4.4 사진 삭제

- 사진 썸네일을 누르면 확대 보기 + **삭제** 버튼
- 삭제는 두 단계: `storage.remove([path])` → `cleaning_photos` 행 delete.
  **스토리지를 먼저 지운다.** DB 행만 지우면 파일이 고아로 남는다
- 삭제 확인 한 번 받는다 ("이 사진을 삭제할까요?")
- RLS상 **올린 본인과 owner만** 지울 수 있다. 남의 사진에는 삭제 버튼을 아예 안 그린다
- 스토리지 삭제가 실패하면 DB 행을 지우지 말고 에러를 보여준다

## 5. 예약 달력 `src/app/(app)/calendar/page.tsx`

### 5.1 데이터

```
reservations (status <> 'cancelled')
  + properties (name, color)
  + cleaning_tasks (status, planned_date, scheduled_date, assignee)
범위: (오늘 - 30일) ~ (오늘 + 90일)
```

**지금 입실 중인 예약이 반드시 보여야 한다.** `checkin_date <= 오늘 <= checkout_date` 인 건이
빠지지 않도록 범위 조건을 `checkout_date >= 시작 and checkin_date <= 끝` 으로 잡는다.
`checkin_date` 만으로 필터하면 이미 입실한 예약이 사라진다.

### 5.2 폰 — 목록형이 기본

세로로 스크롤하는 **주 단위 목록**.

```
─ 8월 3주 (8/17 – 8/23) ─────────
  8/21(금)  퇴실  강릉 KTX 근처 숙소   홍길동
            청소  예정 8/23 · 미완료
  8/25(화)  입실  강릉 KTX 근처 숙소
```

- 오늘 날짜에 표시를 하고, 진입 시 오늘 위치로 스크롤한다
- **거주중인 예약**은 상단에 고정 카드로 따로 보여준다
  (`지금 거주중 · 8/15~8/21 · 홍길동 · 4일 남음`)
- 예약 줄을 누르면 예약 상세로, 청소 줄을 누르면 청소 시트로

게스트 이름은 `reservation_private` 이라 **cleaning 역할에게는 안 보인다.**
없으면 그 자리를 비우고 레이아웃이 깨지지 않게 한다.

### 5.3 태블릿 이상 — 월 그리드

`md` 이상에서 월 달력. 각 칸에 예약 바(숙소 색)와 청소 점을 표시.
지금은 숙소가 하나라 단순하지만 늘어날 것을 가정해 색으로 구분한다.

### 5.4 예약 목록 탭

`/reservations` 는 이번에 **목록만** 만든다 (상세는 다음).
최신순 카드 목록, 상태 필터(전체/예정/거주중/종료/취소).
금액은 `reservation_finance` 가 조회되는 역할에게만 보인다 — 없으면 그 줄을 생략한다.

```sql
select column_name from information_schema.columns
 where table_name = 'cleaning_tasks' and column_name = 'planned_date';

select c.scheduled_date as 퇴실일,
       (select min(r2.checkin_date) from reservations r2
         where r2.property_id = c.property_id
           and r2.status <> 'cancelled'
           and r2.checkin_date >= c.scheduled_date) as 다음입실,
       c.planned_date, c.status
  from cleaning_tasks c order by c.scheduled_date;
```

화면에서:

1. cleaning 계정으로 맡기 → 날짜 선택 → 그 날짜 섹션으로 카드가 이동하는가
2. 날짜를 마감일 이후로 잡으면 "마감일 초과" 경고가 뜨는가 (저장은 되어야 함)
3. 퇴실일 이전 날짜를 API로 직접 시도 → RPC 가 거부하는가
4. 사진 업로드 → 삭제 → 스토리지에서도 사라졌는가
5. 남의 계정이 올린 사진에 삭제 버튼이 안 보이는가
6. 달력에 **지금 거주중인 예약**이 보이는가
7. cleaning 계정의 달력에 게스트 이름이 안 보이는가

크롤러를 한 번 돌려서 `planned_date` 가 유지되는지 확인한다. **이게 이번 변경의 핵심이다.**

## 7. 판단 기준

- 마이그레이션은 **요약 → 컨펌 → 실행** 순서를 지킨다. 실 운영 DB다
- 스펙과 RLS 가 어긋나면 RLS 가 옳다. 어긋난 지점을 보고한다
- `sync_runs` 경고 배너는 이번 범위가 아니다. 다음에 한다.
  구현할 때 주의 — `sync_runs` 는 실패가 없어도 0행, 권한이 없어도 0행이라 구분되지 않는다.
  **역할을 먼저 확인해서 owner·reservation 이 아니면 배너 자체를 렌더링하지 않는다**

## 실제 구현 노트

### 1. `supabase gen types` 가 nullable 인자를 표현하지 못한다

`set_cleaning_planned_date(p_task_id uuid, p_date date)` 의 `p_date` 는 null 을 받는다(예정일 해제).
그런데 생성된 타입은 `Args: { p_date: string; p_task_id: string }` 로 나온다 — null 이 빠져 있다.
호출부에서 캐스트한다. **RLS·함수 쪽이 옳고 타입 생성기가 표현을 못 하는 것**이라 SQL 은 그대로 뒀다.

```ts
p_date: date as unknown as string
```

### 2. `coalesce()` 표현식 인덱스는 괄호 한 겹으로 통과한다

`create index ... on t (coalesce(a, b), c)` 가 그대로 적용됐다.
PostgreSQL 파서가 `COALESCE(...)` 를 함수 호출 형태로 취급하기 때문이다(괄호를 더 두를 필요 없음).
Docker 가 없어 `supabase start` 로 리허설하지 못했지만, `db push` 는 마이그레이션을 트랜잭션으로
감싸므로 실패해도 전부 롤백된다 — 실제로 한 번에 통과했다.

### 3. '지금 거주중' 을 놓치지 않으려면 범위 조건이 중요하다

`checkin_date` 로만 거르면 이미 입실해서 거주중인 예약이 목록에서 사라진다.
`checkout_date >= 시작 and checkin_date <= 끝` 으로 **기간이 겹치는** 예약을 잡아야 한다.
확인: cleaning 계정 달력 상단에 `지금 거주중 · 8/15 ~ 8/21 · 4일 남음` 이 떴다.

### 4. 조회 범위와 그룹핑 기준이 다르다

DB 조회는 `scheduled_date` 범위(오늘-14 ~ +30)로 하고, 화면 그룹핑은
`coalesce(planned_date, scheduled_date)` 로 한다. 담당자가 예정일을 미루면 그 카드가
조회 범위 밖으로 나갈 수 있는데, `scheduled_date` 기준으로 넉넉히 받아 두면 그럴 일이 없다.

`밀린 청소` 판정에는 예외를 하나 뒀다 — **마감일이 지났는데 미완료면 예정일이 미래여도 밀린 청소**로
넣는다. 안 그러면 예정일을 계속 미루는 것만으로 카드가 미래 섹션으로 도망간다.

### 5. 조회 범위 밖으로 나가는 청소 건은 '지난 청소' 로 간다

조회가 오늘-14일부터라 지난 날짜의 완료 건이 생긴다. 04 문서에서 추가한 `지난 청소` 섹션이
그대로 쓰인다.

### 6. 검증 결과 (2026-08-17)

**`planned_date` 가 크롤러 실행 후에도 유지된다 — 이번 변경의 핵심.**
`sync_cleaning_task()` 트리거의 `on conflict do update set` 이 `scheduled_date`·`property_id`·
`status`·`needs_attention`·`updated_at` 만 지정하므로 `planned_date` 는 건드려지지 않는다.
실제로 `planned_date=2026-08-23` 을 넣고 크롤러(run #7)를 돌린 뒤에도 그대로였다.

RPC 가드 — 실제 `cleaning` 계정으로 확인:

| 시도 | 결과 |
|---|---|
| 퇴실일 +2일 | 성공, DB 반영 |
| **퇴실일 이전** | **거부** |
| **퇴실일 +31일** | **거부** |
| 퇴실일 +30일 (경계) | 성공 |
| `null` (예정일 해제) | 성공 |
| 테이블 직접 UPDATE | **0행** — RPC 로만 가능 |

사진 삭제 — 스토리지 먼저 지우고 DB 행을 지운다. 업로드 → 삭제 후 **스토리지에서도 사라진 것**을
확인했다(고아 파일 없음).

역할별 노출 — 같은 화면 코드가 역할에 따라 정반대로 렌더된다:

| | cleaning | reservation |
|---|---|---|
| 달력·예약 목록의 게스트 이름 | 안 보임 | 보임 |
| 예약 목록의 금액 | 안 보임 | 보임 |

cleaning 계정으로 렌더한 `/cleaning` · `/calendar` · `/reservations` HTML 전체(스크립트 페이로드 포함)에
게스트 이름·금액·테이블명 **0건**.

날짜 계산은 `npm test` 로 회귀 테스트가 걸려 있다(총 33개).

### 7. 아직 안 한 것

- **폰 실기기 확인** — 날짜 선택 시트, 사진 확대·삭제, 월 그리드는 실기기에서 봐야 한다
- 예약 상세(`/reservations/[id]`) 는 다음 스펙
- `sync_runs` 경고 배너도 다음 스펙
