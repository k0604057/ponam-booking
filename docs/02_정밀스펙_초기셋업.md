## 5. 파일별 지시

### `.gitignore` — 추가한 줄

```
.env*.local
.ponam*
*session*.json
crawler/.auth/
```

`git check-ignore -v <파일>` 로 실효성을 확인할 것. 규칙을 적어두는 것과 실제로 무시되는 것은 다르다.

### `.env.local` (커밋 금지)

```
NEXT_PUBLIC_SUPABASE_URL=https://mbhajdegqoejwzpgnxwl.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=sb_publishable_...
SUPABASE_SERVICE_ROLE_KEY=sb_secret_...
```

**신형 API 키 체계다.** anon key 는 대시보드에 `sb_publishable_...`, service_role 은 `sb_secret_...` 로
표시된다. 구형 JWT(`eyJ...`) 가 아니다.

단일 환경이라 **로컬 개발도 실 DB를 본다.** 데이터를 지우거나 대량 수정하는 코드는 `where` 조건을
먼저 확인하고 실행할 것.

### `~/.ponam.env` (저장소 밖, chmod 600 — 크롤러 전용)

```
SUPABASE_URL=<project URL>
SUPABASE_SERVICE_ROLE_KEY=<service_role key>
M33_LOGIN_ID=<33m2 아이디>
M33_LOGIN_PW=<33m2 비밀번호>
M33_SESSION_PATH=/Users/<user>/.ponam/33m2-session.json
```

```bash
mkdir -p ~/.ponam && chmod 700 ~/.ponam
touch ~/.ponam.env && chmod 600 ~/.ponam.env
```

### `src/lib/supabase/admin.ts`

```ts
import 'server-only';

export const supabaseAdmin = createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL!,
  process.env.SUPABASE_SERVICE_ROLE_KEY!,
  { auth: { persistSession: false } }

```

### `src/lib/supabase/server.ts` / `client.ts`

`@supabase/ssr` 의 `createServerClient` / `createBrowserClient` 표준 패턴.
쿠키 핸들링은 async `cookies()` 시그니처에 맞추고 `getAll`/`setAll` 을 쓴다.
서버 컴포넌트에서는 쿠키 쓰기가 막혀 있으므로 `setAll` 의 예외는 삼킨다(세션 갱신은 middleware 담당).

클라이언트는 전부 **함수 안에서** 생성한다. 모듈 로드 시점에 만들면 env 가 비어 있는 빌드에서 깨진다.

### 마이그레이션 파일

별도 제공된 두 파일을 **바이트 그대로** 넣는다. 직접 편집하지 말 것.

| 파일 | 크기 | SHA-256 |
|---|---|---|
| `20260816090000_init.sql` | 752줄 / 36,944B | `74fb47f1657a4fb7d5e8c55cb230f9c0570639f88a0df310141fe9f181748652` |
| `20260816090100_storage.sql` | 95줄 / 5,514B | `f8c7e29abfcc022e8d2eaa378db862572fbe2dae89ecfb3150ec33542620f8f2` |

Storage 정책을 분리한 이유는 `20260816090100_storage.sql` 머리말에 있다 — 권한이 없으면

> 문서·채팅으로 SQL 을 옮길 때 **선행 공백이 잘린다.** 실제로 두 군데에서 들여쓰기가 유실됐고
> 해시로 잡아냈다. 파일로 옮기고 해시를 대조할 것.

### 첫 호스트 계정 만들기 — **아직 남아 있음**

`profiles.is_active` 기본값이 `false` 라 마이그레이션 직후에는 활성 멤버가 아무도 없다.
Supabase 대시보드에서 계정을 만든 뒤 한 번만 실행한다:

```sql
update profiles set role = 'owner', is_active = true
 where email = '<본인 이메일>';

-- 이메일 오타면 조용히 0행으로 끝난다. 반드시 확인할 것:
select email, role, is_active from profiles where is_active;
```

이후 멤버 추가는 앱의 초대 기능(`invites` + 서버 라우트)으로 한다.

**로그인 후 라우팅 주의:** 승인 대기 상태(`is_active=false`)에서는 본인 `profiles` 행조차 조회되지 않는다.
"profiles 0행"을 오류나 무한 리다이렉트로 처리하지 말고 **"승인 대기 중" 화면**으로 보내야 한다.

### RLS 실사용 검증 — **화면이 붙은 뒤 계정별로** (미완)

1. `cleaning` 계정으로 `reservation_private` / `reservation_finance` 조회 → 0행
2. `cleaning` 계정으로 `entity_type='settlement'` 코멘트 조회 → 0행
3. `is_active=false` 계정으로 `reservations` / `notifications` 조회 → 0행
4. `cleaning` 계정으로 `update cleaning_tasks set scheduled_date='2030-01-01'` → 0행 (RPC로만 변경 가능)

service_role 로는 RLS 를 우회하므로 이 검증은 의미가 없다. 반드시 계정별 로그인으로 한다.

### 청소 담당의 상태 변경은 RPC 로

```ts
await supabase.rpc('claim_cleaning_task', { p_task_id: id });                     // 내가 맡기
await supabase.rpc('claim_cleaning_task', { p_task_id: id, p_claim: false });     // 놓기
await supabase.rpc('set_cleaning_done',   { p_task_id: id, p_note: '수건 부족' }); // 청소완료
await supabase.rpc('set_cleaning_done',   { p_task_id: id, p_done: false });      // 완료 취소
await supabase.rpc('delete_comment',      { p_comment_id: id });                  // 코멘트 삭제
```

RLS 는 "행"만 제한하고 "컬럼"은 제한하지 못한다. UPDATE 정책으로 열어주면 `scheduled_date`·
`needs_attention`·`completed_by` 까지 조작할 수 있어서 RPC 로만 허용한다.

## 8. 앞으로 마이그레이션을 추가할 때

초기 마이그레이션이 `alter default privileges` 로 **앞으로 만들 테이블에도 `authenticated` 권한이
자동으로 붙게** 해뒀다. 편리한 대신 함정이 있다.

- **새 테이블을 만들면 `alter table ... enable row level security` 를 반드시 같이 쓴다.**
  권한은 자동으로 붙지만 RLS 는 자동이 아니다. 한 줄 빠뜨리면 그 테이블은 로그인한 모든 사람에게
  무제한 공개된다.
- **새 함수를 만들면 `revoke all on function <이름>(<인자>) from public, anon;` 을 같이 쓴다.**
  PostgreSQL 은 새 함수의 EXECUTE 를 PUBLIC 에 기본으로 붙이고, `alter default privileges` 로는
  이걸 없앨 수 없다(내장 기본값이 다시 병합된다). 함수마다 직접 회수하는 수밖에 없다.
  RLS 정책 안에서 쓰는 헬퍼라면 `grant execute ... to authenticated` 도 잊지 말 것.
- 민감정보(개인정보·금액)는 기존 컬럼에 덧붙이지 말고 `reservation_private` / `reservation_finance`
  같은 분리 테이블에 넣는다.
