# 포남동 예약관리 — 프로젝트 현황

> repo의 `docs/` 에 두고, 새 세션마다 먼저 읽는다.
> 최종 수정: 2026-08-17

## 1. 무엇을 만드나

삼삼엠투(33m2) 호스트 계정의 예약 정보를 매일 자동 수집해서, 호스트와 관리자들(예약·정산·청소)이
한 화면에서 공유하고 피드백을 주고받는 **내부 업무공유 앱**.

청소는 "청소전 / 청소완료 + 메모"만 다룬다. 청소비 정산은 이 앱에서 관리하지 않는다.

핵심 흐름:

```
33m2 호스트 페이지 ──(하루 두 번 크롤링)──> Supabase Postgres
                                        │
                        퇴실일 기준 청소 일정 자동 생성 (DB 트리거)
                                        │
        예약 달력 · 청소 보드 · 정산 · 코멘트 쓰레드 (Next.js on Vercel)
                                        │
                        알림 (앱 내 → 웹 푸시 → 메일)
```

## 2. 스택

| 영역 | 선택 | 비고 |
|---|---|---|
| 프론트/서버 | Next.js 16 App Router + TypeScript | Server Components 기본, Turbopack |
| UI | Tailwind 4 (유틸리티만, 컴포넌트 라이브러리 없음) | 모바일 우선 |
| DB/인증/스토리지 | Supabase (Postgres + Auth + Storage) | RLS로 역할 분리 |
| 배포 | Vercel | `main` = 운영 자동배포, 브랜치 = 프리뷰 |
| 수집기 | Playwright (TypeScript), 맥미니 launchd 하루 두 번(05:00·14:00) | 저장된 로그인 세션 재사용 |
| 메일 | Resend | 1차 알림 채널 |
| 알림 | 앱 내 알림 → 웹 푸시(PWA) → 메일 | 이 순서로 붙인다 |
| 카카오 알림톡 | 안 쓰는 쪽으로 | 비즈채널 개설 + 템플릿 심사가 필요한데, 홈 화면에 추가한 PWA면 iOS·안드로이드 모두 웹 푸시가 되므로 대체 가능 |

## 3. 환경 — 단일 환경 (운영만)

Supabase 프로젝트 하나(`ponam-booking`) + Vercel 프로젝트 하나. dev 환경은 두지 않는다.
쓰는 사람이 소수라 환경을 나누는 비용(+$10/월, 관리 부담)이 이득보다 크다고 판단했다.

대신 **단일 환경이라서 생기는 위험을 이렇게 막는다**:

- 스키마 변경은 **반드시 `supabase/migrations/` 파일로만** 한다. 콘솔에서 직접 테이블을 고치지 않는다.
- 마이그레이션은 **추가형을 기본**으로 한다. 컬럼을 지우거나 이름을 바꾸는 대신 새로 추가하고 옮긴다.
- **변경형(UPDATE)·파괴형(DROP/DELETE)은 실행 전 `count` 로 영향 건수를 확인**하고 보고 → 컨펌 → 실행.
- 위험한 마이그레이션은 적용 직전에 **Supabase 대시보드에서 수동 백업**을 하나 뜬다.
  (Pro 플랜은 일일 자동 백업이 있지만, 그 사이에 날린 건 못 되돌린다)
- 겁나는 변경은 맥미니에서 `supabase start`(로컬 Docker)로 **리허설**한 뒤 올린다. 비용 0원.

실사용자가 늘거나 결제가 얽히면 그때 dev를 분리한다. 마이그레이션 파일로만 스키마를 관리해두면
그때 프로젝트 하나 더 만들어 `db push` 하는 것으로 끝난다.

### 다른 개발 건과의 분리

Supabase Pro는 **조직당 $25**, Vercel Pro는 **팀당 $20/인**이다. 격리하겠다고 조직·팀을 새로 만들면
구독이 하나 더 붙는다. 격리는 **프로젝트 단위로 이미 충분**하므로 기존 조직·팀 안에 프로젝트만 추가한다.

| | 새로 만드는 것 | 기존 것을 쓰는 것 |
|---|---|---|
| Supabase | 프로젝트 `ponam-booking` 1개 | 조직 |
| Vercel | 프로젝트 `ponam-booking` | 팀 |
| GitHub | repo `ponam-booking` | 계정 |
| 개발머신 | 폴더 `~/ponam-booking` | — |

비용: Supabase는 프로젝트마다 컴퓨트가 따로 붙는다. Pro에 포함된 $10 컴퓨트 크레딧은 조직당 1개
(Micro 1대분)이고 기존 프로젝트가 이미 쓰고 있으므로, 프로젝트 하나 추가에 **+$10/월**.
Pro 프로젝트는 일시정지가 안 되니 만들면 계속 나간다.

새 조직·팀을 만들 이유는 **청구서를 분리해야 할 때**(사업자 경비 처리 등) 하나뿐이다.

### 무엇이 격리되고 무엇이 공유되나

**격리된다 (다른 프로젝트에 영향 없음)**

- Supabase: DB 인스턴스, URL, anon/service_role 키, 스토리지, Auth 사용자, 마이그레이션.
  이 프로젝트 DB가 죽어도 다른 프로젝트는 멀쩡하다.
- Vercel: 빌드, 배포, 환경변수, 도메인, 함수 런타임, 롤백.
  여기서 빌드가 깨지거나 배포를 되돌려도 다른 프로젝트는 건드려지지 않는다.

**공유된다 (주의할 것)**

- **사용량·요금이 합산된다.** Supabase는 DB 용량·트래픽·MAU 할당량이 조직 안에서 풀로 묶이고,
  Vercel도 Pro 크레딧을 팀 전체가 나눠 쓴다. 한 프로젝트가 폭주하면 다른 프로젝트의 여유분을 먹는다.
- **Vercel 지출 한도에 걸리면 팀의 모든 프로젝트 운영 배포가 한꺼번에 멈춘다.** 이게 유일하게
  실질적인 공동 장애 지점이다. 한도를 넉넉히 잡고, 자동 일시중지는 켤지 말지 의식적으로 정할 것.
- 멤버 권한이 조직·팀 단위다. 누굴 초대하면 다른 프로젝트도 보인다.
- Vercel의 **팀 공유 환경변수(Shared Environment Variables)는 쓰지 않는다.** 프로젝트별로만 설정한다.

대응은 세 가지면 충분하다: ① Vercel 지출 한도 설정 + 알림 켜기, ② Supabase 조직 사용량 알림 켜기,
③ 크롤러는 하루 두 번 고정 스케줄이라 폭주하지 않는다. 실패는 `sync_runs` 에 남기고 종료하며,
다음 실행에서 다시 시도한다. 연속 실패가 쌓이면 알림을 보내는 것은 추후 과제.

## 6. 역할 (앱 내부 권한)

| 역할 | 볼 수 있는 것 | 할 수 있는 것 |
|---|---|---|
| `owner` (호스트) | 전부 | 전부. 사용자 초대·역할 부여. 예약 삭제 |
| `reservation` | 예약 전체 + 게스트 연락처 + 금액 + 변경 이력 | 예약 수정, 청소 일정 조정 (삭제는 불가) |
| `settlement` | 예약 금액·정산 + 예약·청소 현황(활성 멤버 공통) | 정산 작성·확정 (청소 처리는 불가) |
| `cleaning` | 청소 일정, 숙소·날짜 (게스트 연락처·금액은 안 보임) | 청소 건 맡기, 청소완료 처리, 메모·사진·코멘트 |

활성 멤버끼리는 서로의 이름·이메일·연락처를 볼 수 있다(업무 연락용).

**초대로만 들어온다.** Supabase Auth의 공개 가입을 꺼두고, `profiles.is_active` 기본값도 `false` 다.
가입만 해서는 아무것도 보이지 않고, 초대 수락(또는 호스트 승인)이 있어야 멤버가 된다.
반대로 `is_active = false` 로 바꾸는 것이 곧 계정 해지다 — 그 순간 모든 조회·RPC가 막힌다.

청소 담당의 상태 변경은 테이블 UPDATE가 아니라 `claim_cleaning_task()` / `set_cleaning_done()`
함수로만 가능하다. RLS는 행만 제한하고 컬럼은 제한하지 못해서, UPDATE를 열어주면 담당자가
청소 일정이나 감사 플래그까지 마음대로 고칠 수 있기 때문이다.

**민감정보는 컬럼이 아니라 테이블로 분리한다.** Supabase에서는 모든 로그인 사용자가 같은 DB 롤(`authenticated`)이라
컬럼 단위로 역할을 나눌 수 없고, 클라이언트가 `?select=` 로 아무 컬럼이나 지정할 수 있어 "앱에서 가린다"는 방어가 안 된다.

| 테이블 | 내용 | 접근 |
|---|---|---|
| `reservations` | 숙소·기간·상태·공용 메모 | 활성 멤버 전원 |
| `reservation_private` | 게스트 이름·연락처, 크롤 원본 `raw` | owner, reservation |
| `reservation_finance` | 매출·수수료·순수익 | owner, reservation, settlement (쓰기는 앞의 둘) |

정산 코멘트 쓰레드(`entity_type='settlement'`)도 owner/settlement만 읽고 쓴다.
비활성 계정(`is_active=false`)은 모든 조회가 차단된다 — 이게 실질적인 계정 해지 수단이다.

## 7. 화면 (1차 범위)

**모바일 우선.** 청소 담당·관리자는 대부분 폰으로 쓴다. 데스크톱은 호스트가 정산 볼 때 정도다.
그래서 화면은 **폰 기준으로 먼저 설계하고 넓은 화면에서 늘어나게** 만든다. 반대로 하지 않는다.

지켜야 할 것:

- 기본 레이아웃은 한 칼럼. 표를 쓰지 않는다 — 폰에서 가로 스크롤이 생기면 진 것이다.
  예약·청소 목록은 카드로 쌓는다.
- 하단 탭 내비게이션(청소 / 달력 / 예약 / 더보기). 상단 햄버거 메뉴는 엄지가 안 닿는다.
  탭은 **아이콘 + 라벨**을 같이 둔다(아이콘만 두면 못 알아본다). 높이 56px + `env(safe-area-inset-bottom)`
  만큼 하단 패딩(아이폰 홈 인디케이터). 역할에 따라 탭을 숨기지 않는다.
- 주요 액션 버튼(**청소완료**)은 최소 44px 높이에 화면 아래쪽. 한 손으로 누를 수 있어야 한다.
- 사진 첨부는 파일 선택이 아니라 **카메라 바로 열기**(`<input type="file" accept="image/*" capture="environment">`).
  업로드 전 클라이언트에서 리사이즈한다. 폰 원본은 몇 MB씩 된다.
- 달력은 폰에서 월 그리드가 답답하다. **주 단위 / 목록형을 기본**으로 하고 월 뷰는 태블릿 이상에서.
- 로그인 유지가 중요하다. 청소 갈 때마다 다시 로그인하게 만들면 안 쓴다.
- 홈 화면에 추가(PWA)해서 앱처럼 쓰게 한다. manifest + 아이콘 정도면 된다.
  iOS도 홈 화면에 추가하면 웹 푸시를 받을 수 있어서, 카카오 알림톡 없이도 알림이 가능하다.

화면 목록 (대시보드는 두지 않는다. `/` 는 `/cleaning` 으로 보낸다):

1. **청소 보드 (홈)** — 날짜별 목록, 상단에 오늘 요약 한 줄(오늘 퇴실 n · 미완료 n),
   **청소전 / 청소완료** 토글, 메모, 사진
2. **예약 달력** — 폰은 주/목록, 태블릿 이상은 월 그리드. 당일 턴오버 강조
3. **예약 목록·상세** — 기간·금액·상태, 변경 이력, 코멘트 쓰레드
4. **정산** — 월별 매출·수수료·순수익, 확정 처리
5. **더보기** — 내 정보, 숙소, 멤버 초대·역할, 동기화 로그(`sync_runs`), 로그아웃

## 8. 리스크

- **크롤링 안정성** — 33m2에 공개 API가 없는 것을 확인했다(2026-08). 호스트 웹은 Next.js 서버 렌더링이라
  데이터가 HTML에 실려 오고, XHR은 분석 도구뿐이다. 그래서 Playwright로 DOM을 읽는다.
  마크업이 바뀌면 깨지지만, **수집 0건이면 DB를 건드리지 않는** 안전장치가 있어 조용히 망가지지는 않는다.
  실패는 `sync_runs` 에 남는다. 이력은 더보기 → 동기화 로그에서 보고, 마지막 동기화가 실패 상태면
  청소 보드 상단에 경고 배너를 띄운다. `sync_runs` 는 owner·reservation 만 조회할 수 있으므로
  배너도 그 두 역할에게만 보인다. (다음 스펙에서 구현)
- **세션 만료** — 로그인 세션은 언젠가 끊긴다. 그때는 맥 화면 앞에서 `npx tsx crawler/session.ts` 로
  다시 캡처한다. 캡차·문자 인증 가능성이 있어 자동 재로그인은 하지 않는다.
- **맥 상시 가동** — 맥이 꺼져 있으면 그날 동기화가 밀린다. 크롤러는 매번 전체를 다시 훑는 방식이라
  밀려도 다음 실행에서 복구된다. `sudo pmset -a sleep 0 disksleep 0` 확인.
- **약관** — 본인 계정의 본인 데이터 수집이지만, 33m2 이용약관의 자동화 조항은 한 번 확인해두는 게 좋다.
  하루 두 번, 요청 간 1~2초 간격이라 부담을 주는 수준은 아니다.
- **단일 환경** — 리허설할 dev가 없다. 3번의 마이그레이션 규칙이 유일한 안전장치다.

## 9. 작업 방식

- Cowork(이 세션) = 설계·스펙 작성·리뷰. 개발머신 Claude Code = 구현·빌드·commit·push·마이그레이션 실행.
- 실행이 필요한 일은 "정밀 스펙"으로 받아서 개발머신 Claude Code에 붙여넣는다.
- 마이그레이션은 파일명 전체를 정확히 지정하고, 요약 → "실행해" 컨펌 → 실행 순서를 지킨다.
