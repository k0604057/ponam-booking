## 1. 목표

화면 전환이 느리다는 실사용 피드백을 **측정해서** 잡는다. 추측으로 고치지 않는다.
그리고 달력 목록이 오늘부터 시작하게 바꾼다.

## 2. Vercel 리전

Supabase 는 `ap-northeast-2`(서울)에 있다. Vercel 함수 기본 리전은 보통 `iad1`(미국 워싱턴)이다.
이러면 화면 하나 그릴 때마다 **서울 → 미국 → 서울** 을 왕복한다.

```
Vercel → ponam-booking → Settings → Functions → Function Region → Seoul (icn1)
```

코드에서도 고정한다:

```ts
export const preferredRegion = 'icn1';
```

## 3. 측정

고치기 전에 어디서 시간이 가는지 숫자로 확보한다. **임시 계측이 아니라 남겨둔다** — 나중에 또 느려진다.

`src/lib/perf.ts` 의 `perf()` / `perfStart()` 로 `[perf] 화면:구간 123ms` 형식으로 남긴다.
Vercel 대시보드 Logs 에서 `[perf]` 로 걸러 본다.

재는 구간: 미들웨어 `getUser()`, 각 Supabase 쿼리, 페이지 전체.

## 4. 고칠 것

### 4.1 N+1 쿼리
청소 건마다 "다음 입실일" 을 따로 조회하면 안 된다. 기간 내 예약을 **한 번에** 가져와
`property_id` 별로 묶어 메모리에서 맞춘다.

### 4.2 순차 쿼리
서로 의존하지 않는 쿼리는 `Promise.all` 로 묶는다.

### 4.3 로딩 UI 부재
각 라우트에 `loading.tsx`(스켈레톤). 하단 탭은 누른 즉시 활성 표시로 바뀌게 한다.
실제 속도를 안 줄이지만 체감은 가장 크게 바뀐다.

### 4.4 미들웨어 범위
matcher 에서 `_next`, favicon, manifest, 아이콘, 확장자 붙은 파일을 전부 제외한다.
**`/invite` 제외는 지우지 말 것.**

### 4.5 탭 링크 프리페치
하단 탭은 `next/link` 여야 한다. `router.push` 나 `<a>` 면 프리페치가 안 된다.

## 5. 달력 정렬

- **기본은 오늘부터 앞으로**, 가까운 날짜가 위
- **지난 예약은 접어둔다.** `▸ 지난 예약 보기 (n건)`, 펼치면 **최신순(내림차순)**
- 진입 시 스크롤을 오늘로 옮기는 처리는 **없앤다**
- 거주중 예약 고정 카드는 그대로 맨 위
- `/reservations` 목록은 기록 성격이라 **최신순 그대로** 둔다

## 측정 결과

측정 환경: **개발머신(서울) ↔ Supabase(서울)**. 각 화면 7회 요청, 첫 요청은 워밍업으로 버린 중앙값.
Vercel 함수가 `icn1` 일 때의 근사치다.

### 화면 전체 (TTFB, 미들웨어 포함)

| 화면 | 개선 전 | 개선 후 | |
|---|---|---|---|
| `/cleaning` | **158ms** | **77ms** | −51% |
| `/calendar` | 106ms | 82ms | −23% |
| `/more` | 127ms | 77ms | −39% |
| `/reservations` | 81ms | 76ms | −6% |

### 서버 컴포넌트 구간

| 구간 | 개선 전 | 개선 후 | |
|---|---|---|---|
| `cleaning:total` | **97ms** | **27ms** | −72% |
| `calendar:total` | 47ms | 29ms | −38% |
| `more:total` | 68ms | 24ms | −65% |
| `mw:getUser` | 23ms | 21ms | (변화 없음 — 뺄 수 없는 왕복) |
| `mw:profile` | 21ms | 20ms | (변화 없음) |

### 무엇이 줄었나 — 왕복 횟수

**Supabase 왕복 1회가 서울↔서울에서 약 20~25ms 다.** 시간의 대부분이 이 왕복 횟수다.

| 화면 | 개선 전 | 개선 후 |
|---|---|---|
| `/cleaning` | 6회 순차 (mw 2 + getUser + profile + tasks + checkins) | **3회분** (mw 2 + 쿼리 2개 병렬) |
| `/more` | 5회 순차 | **3회분** |
| `/calendar` | 4회 순차 | **3회분** |

### 리전이 왜 가장 큰가

위 숫자는 함수와 DB 가 **같은 리전**일 때다. 함수가 `iad1`(미국)이면 왕복 1회가 20ms 가 아니라
**200~280ms** 가 된다. 왕복 횟수가 그대로 곱해진다.

| | 왕복/화면 | icn1 (실측 기반) | iad1 (왕복 250ms 가정) |
|---|---|---|---|
| 개선 전 | 6회 | ~150ms | **~1,500ms** |
| 개선 후 | 3회 | ~77ms | ~750ms |

**리전이 `iad1` 이면 왕복 횟수를 반으로 줄여도 여전히 0.75초다.** 리전을 먼저 맞춰야 한다.
Vercel 대시보드 확인은 사람이 한다 — 코드에는 `preferredRegion = 'icn1'` 을 넣어뒀다.

배포 후 Vercel Logs 에서 `[perf] mw:getUser` 값을 보면 바로 판별된다:
**20~30ms 면 icn1, 200ms 를 넘으면 리전이 멀다.**

## 실제 구현 노트

### 1. N+1 은 없었다 — 문제는 순차 왕복이었다

스펙 4.1 이 의심한 "청소 건마다 다음 입실일 조회" 는 이미 한 번에 가져오고 있었다
(스펙 #5 구현 때 그렇게 만들어 뒀다). 실제 원인은 **서로 무관한 쿼리를 줄줄이 await 한 것**과,
**미들웨어와 페이지가 같은 조회를 두 번씩 한 것**이었다.

### 2. 미들웨어가 검증한 신원을 헤더로 넘긴다 — 왕복 2회 절약

미들웨어는 `getUser()` + `profiles` 를 부르고, 페이지도 똑같이 또 불렀다. 화면마다 왕복 2회가 낭비였다.

미들웨어가 검증한 값을 요청 헤더(`x-ponam-user`, `x-ponam-role`)로 넘기고
페이지는 `getViewer()` 로 읽는다. `src/lib/auth/viewer.ts`.

- 클라이언트가 같은 이름의 헤더를 보내도 미들웨어가 **무조건 지우고 덮어쓴다**
- 이 값은 **화면을 그리는 데만** 쓴다. 데이터 접근 통제는 여전히 RLS 가 한다
- 위조 시도를 실제로 테스트했다 (`x-ponam-role: owner`) → 무시되고 307 로 차단됐다

### 3. `loading.tsx` 를 넣으면 `redirect()` 가 HTTP 리다이렉트가 아니게 된다

`/more/members` 의 owner 가드를 페이지 안 `redirect('/more')` 로 두고 `loading.tsx` 를 추가했더니,
cleaning 계정 요청이 **307 이 아니라 200** 을 받았다.

스트리밍 SSR 이라 **로딩 스켈레톤이 먼저 200 으로 나가고** redirect 는 그 뒤 스트림으로 전달되기 때문이다.
본문에는 스켈레톤만 있어 데이터가 새지는 않았지만(확인함), 진짜 리다이렉트가 아니다.

**owner 전용 화면 차단을 미들웨어로 옮겼다.** 역할을 이미 알고 있으므로 렌더 자체를 하지 않고 307 로 끝난다.
페이지 안의 가드는 방어를 겹쳐두는 용도로 남겨뒀다.

> 교훈: `loading.tsx` 가 있는 라우트에서 **인가 판정을 페이지 안 `redirect()` 에 의존하지 말 것.**

### 4. 탭 즉시 반응은 `useLinkStatus` 로

`next/link` 의 `useLinkStatus()` 를 Link 자손 컴포넌트에서 읽어, 누른 탭이 서버 응답을 기다리지 않고
바로 활성색으로 바뀌게 했다. 아이콘에 `animate-pulse` 를 걸어 진행 중임을 보여준다.
탭은 원래부터 `next/link` 라 프리페치는 이미 되고 있었다 (스펙 4.5 는 해당 없음).

### 5. 인덱스 확인은 지금 데이터로는 의미가 없다

`cleaning_tasks` 가 **3행**이다. 이 크기에서 PostgreSQL 은 인덱스가 있어도 Seq Scan 을 고른다 —
전체를 읽는 게 인덱스를 타는 것보다 싸기 때문이다. **그게 정상이고 문제가 아니다.**

`explain analyze` 는 SQL 에디터가 필요해 여기서 돌리지 못했다(psql 접속 정보 없음).
행이 수천 단위가 된 뒤에 확인하는 게 맞다. 그때 `cleaning_tasks_planned_idx` 를 타야 한다.

### 6. 검증

- 인증 회귀 **15/15 통과** — 비로그인 리다이렉트, 활성 멤버 접근, owner 전용 차단(307),
  헤더 위조 무시, 해지 계정 `/pending`, API 401/403
- `/more/members` 차단 시 **본문에 멤버 데이터가 없음**을 바이트 단위로 확인
- 달력: 거주중 카드 → `지난 예약 보기 (6건)`(접힘) → `8월 3주 (이번 주)` 순.
  과거 주는 펼치기 전까지 렌더되지도 않는다
